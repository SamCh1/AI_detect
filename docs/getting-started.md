# Getting started

Onboarding for a new contributor: install one tool, run one command, understand
what you are looking at.

The root [`README.md`](../README.md) has the short version — the `make` targets
and the three rules the Makefile enforces. This document is the walkthrough:
how to get `uv`, what a successful first run prints, and what to do when it
does not. It deliberately does **not** restate the target list; if the two ever
disagree, the README and `make help` are right.

---

## 1. Install uv — the only prerequisite

Do **not** install Python. uv downloads and manages the 3.11 interpreter both
apps pin, which is the entire point: no pyenv, no Homebrew python, no
`apt install python3`, and nothing that depends on what your OS happens to ship.

```bash
# macOS / Linux
curl -LsSf https://astral.sh/uv/install.sh | sh

# macOS, if you prefer Homebrew
brew install uv

# Windows (PowerShell)
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"
```

Then confirm it is on your PATH — open a new shell first, the installer edits
your profile:

```bash
uv --version
```

> **macOS users:** your system `python3` is 3.9 and lives inside Xcode. It
> cannot run either app. That is expected and you can ignore it — nothing in
> this repo uses the system interpreter any more. See
> [Troubleshooting](#python3---version-says-396) if it confuses you later.

---

## 2. First run

```bash
git clone https://github.com/SamCh1/AI_detect.git
cd AI_detect
make setup
```

On macOS and Linux this needs `make`, which you almost certainly have. On
Windows, skip `make` entirely and run the two commands it wraps:

```bash
uv sync --directory fall_detection_web --locked
uv sync --directory simple_ai_vision  --locked
```

The first run downloads CPython 3.11 plus roughly 800 MB of torch and YOLO
weights for `fall_detection_web`, so give it a few minutes. Later runs are
seconds — uv caches everything globally and hardlinks into each venv.

`make setup` ends by running `make doctor`. A healthy repo looks like this:

```
-- toolchain
  uv                         uv 0.11.26
  pinned python              3.11, both apps (.python-version)
-- venvs
  fall_detection_web/.venv   ready   Python 3.11.15
  simple_ai_vision/.venv     ready   Python 3.11.15
-- lockfiles
  fall_detection_web/uv.lock agrees with pyproject.toml
  simple_ai_vision/uv.lock   agrees with pyproject.toml
```

Both venvs `ready`, both lockfiles `agrees`. Anything else, see
[Troubleshooting](#troubleshooting).

Run `make dev` and you have both apps up: vision on :8000, fall on :8090.

## 3. What you are actually looking at

Two unrelated apps in one repository. They share a git remote and nothing else —
no shared code, no shared dependencies, no shared virtualenv.

| | `simple_ai_vision/` | `fall_detection_web/` |
|---|---|---|
| what it is | Home Assistant add-on | standalone web app |
| ships as | Alpine container, built by HA | venv + systemd on a VPS |
| dependencies | **exactly 3** direct | torch, YOLO, ~13 direct |
| port | 8000 | 8090 |

Each owns a `pyproject.toml`, a `uv.lock` and a `.venv` **inside its own
directory**. This separation is load-bearing, not tidiness: `simple_ai_vision`
has a hard three-dependency ceiling and a ~25-entry DO-NOT-ADD list. If the two
apps shared one environment, an accidental `import torch` in the add-on would
work perfectly on your laptop and fail for every user, because the shipped
Alpine image does not contain torch. Separate locked environments make that
mistake impossible to install rather than merely discouraged.

## 4. The daily loop

**Running code:**

```bash
make preflight      # ready for make dev? verdict + exit code
make dev            # both apps, labelled output streams
make dev-fall       # just fall_detection_web, :8090
make dev-vision     # just simple_ai_vision, :8000
make check          # byte-compile both — a syntax gate, not a linter
```

There is no test suite, linter or CI. `make check` proves both apps parse and
nothing more. Do not read a green `make check` as "it works".

**Changing a dependency** — the one workflow that has a required order:

```bash
# 1. edit the app's pyproject.toml  (NOT requirements.txt)
# 2. re-resolve and re-export
make lock
# 3. rebuild your venv from the new lock
make setup
# 4. commit pyproject.toml, uv.lock AND requirements.txt together
```

Three rules, each of which the tooling enforces rather than trusts:

- **Never `pip install` into a `.venv`.** It produces an environment no
  lockfile describes, which is the exact failure this layout prevents. Nothing
  will stop you locally; it will diverge silently from every other machine.
- **Never hand-edit `requirements.txt`.** Both are generated by `make lock`.
  They exist only because the two deploy paths still install with pip — the
  add-on's Dockerfile and the VPS systemd venv. `make lock` overwrites whatever
  you typed.
- **Adding a 4th dependency to `simple_ai_vision` is a design change**, not a
  chore. Read its [`AGENTS.md`](../simple_ai_vision/AGENTS.md) first.

## 5. Troubleshooting

### `uv.lock` says STALE, or setup refuses to run

```
The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.
```

Someone edited a `pyproject.toml` without re-locking. Run `make lock`, then
commit the regenerated `uv.lock` and `requirements.txt` alongside it.

This refusal is intentional. `make setup` uses `uv sync --locked`, which will
not silently re-resolve your dependencies into something no lockfile records.

### `python3 --version` says 3.9.6

On macOS that is Xcode's bundled Python, reached through the `/usr/bin/python3`
shim. It is not used by this repo and does not need fixing. Both apps run the
3.11 that uv installed, inside `.venv`. To see the interpreter that actually
matters:

```bash
fall_detection_web/.venv/bin/python -V     # Python 3.11.x
```

If you want a modern `python3` on your PATH for unrelated work, that is
`uv python install 3.11` — but this repo never needs it.

### A venv says `missing` in `make doctor`

```bash
make setup          # builds whatever is absent
make reset          # or: delete both venvs and rebuild from scratch
```

`make reset` also clears `__pycache__`. It does not touch `.env` or `data/`.

### Can I use Python 3.12 or 3.13?

No — 3.11 is pinned deliberately and 3.13 is impossible today.
`torchvision==0.20.1` publishes wheels for cp39 through cp312 only, so 3.13
cannot resolve at all:

```
hint: You require CPython 3.13 (cp313), but we only found wheels for
      torchvision (v0.20.1) with ABI tags: cp39, cp310, cp311, cp312
```

3.11 specifically, rather than 3.12, because `simple_ai_vision` ships on
`python:3.11-alpine` — matching it means your venv and the shipped container
run the same interpreter. Moving off 3.11 means bumping torch and re-validating
the detection pipeline.

### `make: command not found` (Windows)

Expected — `make` is a convenience wrapper, not a requirement. The two
`uv sync` commands in [First run](#2-first-run) do exactly what `make setup`
does. Everything else in the Makefile is Docker and code-index tooling that
Windows contributors do not need for app work.
